## Research question

Which of the 12 practice genes change after treatment, and does your analysis find the four changes
we built in?

The reads behind this project were simulated: generated by a computer from a known recipe, with
chosen genes made to change by chosen amounts. In real experiments you never know the true answer.
Here you can check every step against the truth, which is the best way to learn what each tool does
and where it falls short.

## What you will build

**In:** `data/practice_counts.txt` (featureCounts output, 12 genes × 4 samples) and
`data/practice_samples.csv` (the sample sheet). See `data/README.md`.

**Out:** one script, `scripts/counts_to_results.R`, and in `results/`:

| Task | File | What it holds |
|---|---|---|
| 1 | `library_sizes.csv` | columns `sample`, `library_size` |
| 2 | `deseq2_results.csv` | the full DESeq2 results, one row per gene, with a `gene` column first |
| 2 | `significant_genes.csv` | columns `gene`, `log2FoldChange`, `padj`: genes with padj < 0.05 |
| 3 | `truth_comparison.csv` | columns `gene`, `truth`, `deseq2`, `cpm`: one row per built-in gene, plain ratios |
| 4 | `volcano.png` | the volcano plot with the significant genes labelled |
| 4 | `methods.md` | your methods paragraph and a `## Limitations` section |

The TODO comments in the script give the exact code for saving the files the check reads.

## Before you start

1. Get your own copy of this repository. Use the GitHub Classroom invitation link in the project
   lesson on lsma.co.uk, or click **Use this template** on GitHub.
2. Clone your copy to your computer and open the folder in RStudio as a Project
   (File > New Project > Existing Directory).
3. You need R with DESeq2 (from Bioconductor, as in Module 4, lesson 1), ggplot2 and ggrepel.
4. Work in `scripts/counts_to_results.R`, write every output to `results/`, and never edit `data/`.

Predict before you run: you know which genes should change and in which direction, so write your
expectation down first. Remember the scale: with 12 genes and 2 samples per group, this is far smaller
than a real experiment, and some of what you see comes from that small size.

## Tasks

### 1. Counts

Read `practice_counts.txt` with `read.delim(..., comment.char = "#")`, keep the four count columns,
and give them sample names that match the sample sheet. Check the library size of each sample with
`colSums()`.

Lesson to revisit: Module 4, lesson 1.

**Checkpoint:** 12 genes × 4 samples; library sizes 8,998, 10,999, 10,000 and 8,500; PRG005 has the
most reads in the control samples, and PRG010, which treatment induces, in treat_1.

### 2. Differential expression

Run DESeq2 with `design = ~ condition` and control as the reference. List genes with padj < 0.05.
Some padj values may be NA, so exclude those explicitly.

Lesson to revisit: Module 4, lessons 1 and 2.

**Checkpoint:** DESeq2 finds exactly the four built-in genes: PRG003 and PRG004 up, PRG007 down and
PRG010 up.

### 3. Compare with the truth

The true changes were PRG003 ×4, PRG004 ×3, PRG010 ×2 and PRG007 ×¼. Compare them with DESeq2's fold
changes, and with simple CPM fold changes (each count ÷ the sample's library size × 1,000,000).

Lesson to revisit: Module 4, lesson 2.

**Checkpoint:** DESeq2's estimates are closer to the truth than CPM's but still smaller for the
induced genes (for example about ×2.8 rather than ×4 for PRG003), because with only 12 genes the
normalisation is itself affected by the changes. Real experiments with thousands of genes are much
less affected.

### 4. A volcano plot and a methods paragraph

Draw a volcano plot of your results, labelling the four significant genes. Write a methods paragraph
with every package, version and setting, and two limitations.

Write `results/methods.md` with a `## Methods` heading and a `## Limitations` heading. The methods
name the aligner and counting tool, R and DESeq2 with their versions, the design formula, the
reference level and the cut-off.

Lesson to revisit: Module 4, lesson 3, and Module 3.

**Checkpoint:** four labelled genes on the correct sides; someone could rerun your analysis from your
methods alone; your limitations mention two replicates per group and simulated data.

## Hand in

Commit and push `scripts/` and `results/`. The **Checks** tab (GitHub Actions) then runs
automatically. A green tick means every checkpoint passed. You can push as often as you like.

You can run the same check on your own computer first: `python tests/check_results.py`. It does not
need R: it reads the files you saved, and checks fold changes with a tolerance rather than exact
p-values.

## If a check fails

Open the **Actions** tab, click the latest run and read the log. Each line names a task and says
what to look at, for example:

```
FAIL  Task 2 · Differential expression: the fold changes point the wrong way; is control the reference level?
```

Fix that task, rerun your script, commit the new results and push again.
